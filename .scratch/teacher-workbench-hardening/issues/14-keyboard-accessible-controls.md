## 上一轮未达成项的根因（本轮查明）

上一轮试了两种做法都失败，当时只能把这一项留作未勾选。本轮在**真实浏览器**里查到了确切原因：

```
locator resolved to <li tabindex="-1" role="menuitem" class="ant-dropdown-menu-item">
unexpected value "inactive"
```

**AntD 的下拉菜单项是 `tabindex="-1"`**——它们可以被程序化聚焦，但 focus 不会自己进入菜单。所以：回车能把菜单**展开**（那是按钮自己的 click 行为），但焦点仍留在触发按钮上，按 ArrowDown 没有任何效果，键盘用户永远到不了"退出登录"。这不是测试写得不对，是**真实的键盘陷阱**。

上一轮失败的原因也由此清楚：`autoFocus` 是让焦点无条件进入菜单，展开的**每一次**都抢焦点，于是鼠标悬停展开时也被抢，两条鼠标退出登录用例一起挂掉，只能回退。

## 本轮做法：只在「键盘发起的展开」时把焦点送进菜单

保留了 `autoFocus` 想达到的效果（焦点进菜单），但加了条件——**这次展开是不是键盘发起的**：

- 触发按钮的 `onKeyDown` 里，`ArrowDown` 直接展开并标记为键盘发起（`preventDefault`，否则会滚动页面）；`Enter` / 空格不拦截默认行为，只做标记，交给按钮自身的 click 展开。
- `Dropdown` 改为受控（`open` / `onOpenChange`），并在 `open` 变为 true 时，若标记为键盘发起，则把焦点移到菜单项；移完立即清标记。
- 鼠标悬停 / 点击展开不设标记，因此**不抢焦点**，鼠标路径与外观完全不变。

菜单项一旦获得焦点，rc-menu 自身的键盘处理即接管，ArrowDown / Enter 正常工作。

## 顺手修掉一条"看起来在测、其实没测"的单测

原 `a11y.test.tsx` 里那条用例是这样的：

```ts
const logoutItem = await screen.findByRole('menuitem', { name: /退出登录/ })
logoutItem.focus()          // 手动聚焦
expect(logoutItem).toHaveFocus()
```

它只证明了"程序化聚焦一个菜单项会生效"，**对"键盘用户能否到达那里"零覆盖**——正是这条用例让缺口看起来已被覆盖。已改为断言焦点**自动**进入菜单（不再手动 `focus()`），现在它真的能拦住回归。

## 关于"鼠标体验不变"

上一轮已如实记录：为让按钮可被键盘激活，下拉触发方式由"仅悬停"改为"点击 + 悬停"。纯键盘可达与"鼠标语义完全不变"在这类组件上无法同时满足（键盘激活按钮走的就是 click）。本轮**没有增加新的偏离**——焦点只在键盘发起时移入，鼠标路径与上一轮一致。

## 关于聚焦态

未书写自定义聚焦样式，依赖原生按钮的默认焦点环。该条无自动化断言——jsdom 不做布局与绘制，断言"焦点环可见"在单测里没有意义。

## 过程记录（一个容易反复踩的坑）

## 更正（两轴评审后）

原清单有一行写的是 `[x] 鼠标操作体验与外观不变（见下方说明）`——**这条勾选与本票自己的说明自相矛盾**：紧邻的"关于'鼠标体验不变'"一节白纸黑字写着触发方式已由"仅悬停"改为"点击 + 悬停"，也就是鼠标语义**确实变了**。一个承认了偏离的说明，配一个"不变"的勾选，正是"看起来完成"的典型。

已改为如实表述：鼠标体验**有一处刻意的行为新增**，原验收要求的"完全不变"无法满足。行为本身不打算改回去——纯键盘可达与"鼠标语义完全不变"在这类组件上不可兼得，键盘激活按钮走的就是 click 事件。
