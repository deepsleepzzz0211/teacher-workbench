# 02: CI 质量门

**What to build:** 目前 231 条用例只能靠人肉记得跑，README 里的质量声明没有任何强制力。加上 CI：每次推送自动安装依赖、类型检查、跑全部单元与集成测试、跑构建，任一环节失败即标红。此后任何改动都必须先过这道门。

**Blocked by:** 01 初始化版本控制

**Status:** done

- [x] 推送或提 PR 时自动触发流水线（实测四次运行，均由推送触发）
- [x] 流水线依次执行：依赖安装（`--frozen-lockfile` 锁定版本）→ 类型检查 → 全部单元与集成测试 → 构建
- [x] 任一环节失败则整体失败，并在结果中指明是哪一步（实测：失败精确定位到「类型检查」，后续步骤自动 skipped）
- [x] CI 环境下的后端测试能连上数据库（用 `postgres:15` 服务容器，不依赖 runner 预装 PostgreSQL）
- [x] 故意制造一次类型错误，确认流水线确实变红（**实测**，见下）
- [x] 修复该错误后流水线恢复绿色（**实测**，见下）

## 超出验收的补充

**额外增设端到端任务。** 原验收只要求四个步骤，但 26 条端到端用例是这个项目最有价值的一道整合验证，跳过它等于半个门禁。该任务以 `needs: quality` 依赖主流程，主流程不过就不跑；失败时上传 Playwright 报告便于排查。

**配置 CI 期间发现并修掉的两个问题：**

1. **端到端测试在全新数据库上无法自足。** `e2e` 的 `globalSetup` 只灌种子、不做迁移，在服务容器或任何首次克隆上必然失败——本地一直能过，只因开发库早已迁移过。
   **修正：这一条是在配置 CI 的过程中推演出来的（"全新数据库会怎样"），并非被某次 CI 运行暴露**；修复提交也早于工作流提交。此前写成"CI 暴露"，不准确。
2. **就绪探测不可靠（这一条才是 CI 首轮运行真实暴露的）。** 现改为构建由 `pnpm e2e` 先完成、`webServer` 只负责启动预览，并让 `vite preview` 显式绑定 `127.0.0.1`（原先默认绑 `localhost`，而探测目标是 `127.0.0.1`，在 Linux runner 上可能因 IPv6 解析而探测不到）。修复后 CI 中端到端从 **303 秒超时** 变为 **62 秒通过**。
   **诚实说明：我同时改了两个候选原因（把构建移出就绪预算 + 显式绑定地址），并没有隔离验证究竟是哪一个决定性。** 另外原稿写成"构建耗时会吃掉就绪预算"也不成立——同一份提交里记录的构建耗时只有 13 秒，而就绪预算是 300 秒。

## 复查后的校准（诚实记录）

- **"推送或提 PR 时自动触发"：只验证了推送。** `on: pull_request` 已配置，但四次运行全部由推送触发——PR 路径**配置了但未实测**。
- **`reuseExistingServer` 已从 `true` 改为 `false`。** 复查指出它与我写在 `AGENTS.md` 里的意图相矛盾：该项为 `true` 时，若端口被占用，Playwright 会悄悄复用别的服务（例如跑在 dev server 上），把已记录过的抖动带回来。改为 `false` 后，端口被占用会**直接报错**，与文档意图一致。
  **但请注意：这并没有消除那个抖动。** 改完后本地复跑，在**全新 preview 服务**下仍出现 1 条同类 flaky（登录页元素等待超时，重试后通过）。也就是说，该抖动的成因不是"复用 dev server"——我之前那个归因不完整，更可能是首屏懒加载分包在冷启动/机器有负载时的时序问题。CI 有 `retries: 1` 吸收它，四轮运行中始终为绿。
- **pnpm 版本不再在 CI 中硬编码。** 原先两处写死 `10.30.2`，而 `packageManager` 才是唯一事实来源；现交给 `pnpm/action-setup` 从 `package.json` 读取。
- **CI 的限流阈值统一为 200**，与 `.env.example` 一致（原先 1000 无理由地偏离）。
- **文档同步**：README 与 AGENTS.md 补齐了"CI 是强制质量门"，并更正了 `globalSetup` 的行为描述（现在是先迁移、再灌种子）。

## 顺带记录的数据

修复后的 CI 耗时（Ubuntu runner）：主流程 install 1s / 类型检查 6s / 测试 20s / 构建 16s；端到端 62s。整轮约 3 分钟。
