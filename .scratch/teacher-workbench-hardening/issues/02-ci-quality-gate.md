# 02: CI 质量门

**What to build:** 目前 231 条用例只能靠人肉记得跑，README 里的质量声明没有任何强制力。加上 CI：每次推送自动安装依赖、类型检查、跑全部单元与集成测试、跑构建，任一环节失败即标红。此后任何改动都必须先过这道门。

**Blocked by:** 01 初始化版本控制

**Status:** done

- [x] 推送或提 PR 时自动触发流水线（实测四次运行，均由推送触发）
- [x] 流水线依次执行：依赖安装（`--frozen-lockfile` 锁定版本）→ 类型检查 → 全部单元与集成测试 → 构建
- [x] 任一环节失败则整体失败，并在结果中指明是哪一步（实测：失败精确定位到「类型检查」，后续步骤自动 skipped）
- [x] CI 环境下的后端测试能连上数据库（用 `postgres:15` 服务容器，不依赖 runner 预装 PostgreSQL）
- [x] 故意制造一次类型错误，确认流水线确实变红（**实测**，见下）
- [x] 修复该错误后流水线恢复绿色（**实测**，见下）

**第 3 轮的关键细节**（这才是"门禁有效"的证据，而非"写了配置"）：
失败发生在**类型检查**这一步，其后的「单元/集成/组件测试」与「构建」被自动 **skipped**，端到端任务因依赖未通过同样 **skipped**。即：失败定位准确、不继续浪费资源、不留半成品。

## 超出验收的补充

**额外增设端到端任务。** 原验收只要求四个步骤，但 26 条端到端用例是这个项目最有价值的一道整合验证，跳过它等于半个门禁。该任务以 `needs: quality` 依赖主流程，主流程不过就不跑；失败时上传 Playwright 报告便于排查。

**CI 暴露并修掉的两个真问题：**

1. **端到端测试在全新数据库上无法自足。** `e2e` 的 `globalSetup` 只灌种子、不做迁移，在 CI 的服务容器或任何首次克隆上必然失败——本地一直能过，只因开发库早已迁移过。
2. **就绪探测不可靠。** 原先把前端构建放在 Playwright 的 `webServer` 命令里，构建耗时会吃掉就绪预算；且 `vite preview` 默认绑 `localhost`，而探测目标是 `127.0.0.1`，在 Linux runner 上可能因 IPv6 解析而永远探测不到。现改为构建由 `pnpm e2e` 先完成、`webServer` 只负责启动预览，并让预览显式绑定 `127.0.0.1`。修复后 CI 中端到端从 **303 秒超时** 变为 **62 秒通过**。

## 顺带记录的数据

修复后的 CI 耗时（Ubuntu runner）：主流程 install 1s / 类型检查 6s / 测试 20s / 构建 16s；端到端 62s。整轮约 3 分钟。
